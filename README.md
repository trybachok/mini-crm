# Мини-CRM «Объекты и задачи»

Постановщик ставит задачи по строительным объектам, исполнители берут их в работу и отдают на проверку. Права доступа и переходы статусов проверяет база данных.

**Приложение:** https://mini-crm.dynek.me

| Роль        | Email                 | Пароль        |
| ----------- | --------------------- | ------------- |

| Исполнитель | `ivanov@example.com`  | `executor123` |
| Исполнитель | `petrova@example.com` | `executor123` |

Стек: React 19, TypeScript, Vite, Tailwind, shadcn/ui, TanStack Query; Supabase (PostgreSQL, RLS, SQL-функции).

## Как запустить

```bash
npm install
cp .env.example .env   # VITE_SUPABASE_URL и VITE_SUPABASE_ANON_KEY из настроек проекта Supabase
npm run dev            # http://localhost:5173
```

`npm test` — тесты, `npm run build` — production-сборка.

### База данных

Миграции лежат в `supabase/migrations/` и применяются через Supabase CLI:

```bash
supabase link --project-ref <project-ref>
supabase db push --remote                                  # схема, RLS, функция переходов
supabase db query --remote --yes -f supabase/seed.sql      # тестовые пользователи, объекты, задачи
```

В настройках Auth выключена регистрация (*Allow new users to sign up*). Роль нового пользователя задаётся в user metadata: `{"role": "manager"}` или `{"role": "executor"}`.

`supabase/tests/rls_checks.sql` от имени каждой роли выполняет запрещённые действия (чтение чужой задачи, прямая смена статуса, запись в историю, недопустимый переход) и проверяет, что база их отклоняет:

```bash
supabase db query --remote --yes -f supabase/tests/rls_checks.sql
```

### Деплой

`Dockerfile` собирает статику и раздаёт её через nginx. На сервере: `docker compose up -d --build` с переменными `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` в окружении. HTTPS завершается на внешнем reverse proxy.

## Как это устроено — для руководителя

Приложение состоит из двух частей. **Интерфейс** — страницы в браузере со списками и кнопками; он живёт на нашем сервере и показывает данные. **Хранилище** — облачный сервис Supabase, где лежат объекты, задачи и история. Правила «кому что можно» заложены в хранилище и действуют при любом способе обращения к нему, включая запросы в обход интерфейса. Интерфейс дополнительно прячет недоступные кнопки для удобства.

**Роли.** Постановщик создаёт объекты и задачи, назначает исполнителей, принимает работу или возвращает на доработку, видит всё. Исполнителю доступны ровно две вещи: свои задачи с объектами, где они стоят, и два действия — взять задачу в работу и отправить на проверку. Чужие задачи, создание и правка объектов и задач, приёмка — закрыты для него на уровне хранилища. Пользователей заводит администратор; самостоятельная регистрация выключена.

**Жизнь задачи.** Новая → В работе → На проверке → Принята. С проверки постановщик может вернуть задачу на доработку с обязательным комментарием; исполнитель снова берёт её в работу. Это полный список переходов. Каждый шаг записывается в историю (кто, когда, откуда куда, комментарий); история хранится в неизменяемом виде.

**Данные** хранятся в Supabase отдельно от нашего сервера: при остановке сервера с интерфейсом задачи и история сохраняются. Пароли и секретные ключи хранятся вне кода.

## Решения и допущения

Безопасность:

- Вся защита в базе: RLS на всех таблицах, права выданы точечно по колонкам, у неавторизованных прав нет. Фронтенд скрывает недоступные действия.
- Статус меняется только через SQL-функцию `change_task_status`: она проверяет роль, исполнителя, допустимость перехода и комментарий при возврате. Колонка `status` закрыта для прямой записи всем ролям.
- Историю пишут только триггер создания задачи и эта функция; у пользователей на неё право чтения.
- Роль хранится в таблице `profiles` и читается сервером при каждой проверке.
- Во фронтенд попадает только публичный anon key. Service role key в проекте отсутствует.

Модель данных:

- У задачи один исполнитель и один автор. «Постановщиков и исполнителей может быть несколько» прочитано как «в системе»: любой постановщик видит и принимает любые задачи, исполнителей сколько угодно, у каждого свои. Исполнителя можно сменить в форме редактирования, история сохраняется.
- Исполнитель у задачи может отсутствовать: постановщик создаёт задачу «на потом» и назначает исполнителя позже.
- История начинается с записи о создании задачи (`from_status = null`).
- История принадлежит задаче: текущий исполнитель видит все её записи, включая действия предыдущего исполнителя. После переназначения задача и её история доступны постановщику и новому исполнителю.
- Удаление объекта удаляет его задачи и их историю; перед удалением интерфейс показывает число задач и просит подтверждение. Задание требует неизменяемости записей истории; срок их хранения совпадает со сроком жизни задачи.
- Обязательность комментария при возврате продублирована check-ограничением на таблице истории.
- Миграции только «вперёд» (Supabase CLI работает без down-миграций). Откат изменения — новая миграция.

Интерфейс:

- Правила переходов продублированы на клиенте (`src/domain/taskStatus.ts`) для показа доступных кнопок. Источник истины — база: при расхождении копий пользователь получит ошибку от базы.
- Списки по умолчанию показывают активные задачи (все, кроме принятых); фильтр по статусу хранится в URL. Списки длиннее 50 строк подгружаются кнопкой «Показать ещё».
- Карточка без доступа показывает «не найдено или нет доступа»: база возвращает пустой ответ.
- После входа исполнитель попадает в «Мои задачи», постановщик — в «Объекты».

Вне объёма задания: поиск и фильтр по исполнителю, экран управления пользователями (их заводит администратор в Supabase), живые обновления списков.
