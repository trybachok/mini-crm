# Мини-CRM «Объекты и задачи»

Постановщик ставит задачи по строительным объектам, исполнители берут их в работу и отдают на проверку. 
Права доступа и переходы статусов проверяет база данных.

**Приложение:** https://mini-crm.dynek.me

| Роль        | Email                 | Пароль        |
| ----------- | --------------------- | ------------- |

| Исполнитель | `petrova@example.com` | `executor123` |

Стек: React, TypeScript, Vite, Tailwind, shadcn/ui, TanStack Query; Supabase (PostgreSQL, RLS).

## Как запустить

```bash
npm install
cp .env.example .env   # VITE_SUPABASE_URL и VITE_SUPABASE_ANON_KEY из проекта Supabase
npm run dev
```

База — миграции в `supabase/migrations/`:

```bash
supabase link --project-ref <project-ref>
supabase db push --remote                                  # схема, RLS, функция переходов
supabase db query --remote --yes -f supabase/seed.sql      # тестовые пользователи и данные
supabase db query --remote --yes -f supabase/tests/rls_checks.sql   # проверка правил доступа
```

В Auth выключена регистрация. Роль пользователя задаётся в user metadata: `{"role": "manager"}` или `{"role": "executor"}`.

Деплой: `docker compose up -d --build` с теми же двумя переменными в окружении.

## Как устроено

Приложение состоит из двух частей. **Интерфейс** — страницы в браузере; он показывает данные. 
**Хранилище** — облачный сервис Supabase, где лежат объекты, задачи и история. 
Правила «кому что можно» заложены в хранилище и действуют при любом обращении к нему, включая запросы в обход интерфейса.

**Роли.** Постановщик создаёт объекты и задачи, назначает исполнителей, принимает работу или возвращает на доработку, 
видит всё. Исполнитель видит свои задачи и объекты, где они стоят; может взять задачу в работу и отправить на проверку. 
Остальное для него закрыто на уровне хранилища. Пользователей заводит администратор.

**Жизнь задачи.** Новая → В работе → На проверке → Принята. 
С проверки постановщик может вернуть задачу на доработку с обязательным комментарием; исполнитель снова берёт её в работу. 
Каждый шаг записывается в историю: кто, когда, откуда куда, комментарий. История хранится в неизменяемом виде.

## Решения и допущения

- Вся защита в базе: RLS на всех таблицах, права выданы точечно по колонкам. Интерфейс скрывает недоступные действия, проверяет база.
- Статус меняется только через SQL-функцию `change_task_status`. Она проверяет роль, исполнителя, допустимость перехода и комментарий при возврате. Колонка `status` закрыта для прямой записи.
- Историю пишет только база (триггер и эта функция); у пользователей на неё право чтения.
- Во фронтенд попадает только публичный anon key.
- У задачи один исполнитель и один автор. «Постановщиков и исполнителей может быть несколько» прочитано как «в системе»: любой постановщик видит и принимает любые задачи, у каждого исполнителя свои. Исполнителя можно сменить в форме редактирования.
- История принадлежит задаче: текущий исполнитель видит все её записи, включая действия предыдущего. Бывший исполнитель после переназначения доступ к задаче теряет.
- Исполнитель у задачи может отсутствовать: постановщик назначает его позже.
- Удаление объекта удаляет его задачи с историей, с подтверждением и числом задач.
- Правила переходов продублированы на клиенте (`src/domain/taskStatus.ts`) для показа кнопок. Источник истины — база.
- Списки по умолчанию показывают активные задачи; фильтр по статусу хранится в URL. Длинные списки подгружаются по 50 строк.

Вне объёма задания: поиск, экран управления пользователями, живые обновления списков.
